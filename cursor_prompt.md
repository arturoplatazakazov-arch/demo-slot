`TZ_slot_engine.md` в корне проекта — это техническое задание, которому нужно строго

вопросы"), не додумывай молча критичные для математики игры вещи — выбери разумное
индустриальное значение по умолчанию, явно напиши об этом в комментарии в коде и в конце
ответа списком того, что стоит подтвердить у меня.

Стек: Python 3.12+, FastAPI, Pydantic v2, PostgreSQL + SQLAlchemy + Alembic, NumPy (для
симулятора), pytest. Redis — опционально, добавляй только если реально нужно на этом этапе.

Работай поэтапно, не пытайся сгенерировать всё одним файлом. После каждого этапа — рабочий,
протестированный код, который можно запустить.

## Этап 1 — Скелет проекта
- Структура репозитория (например `app/core`, `app/features`, `app/api`, `app/models`,
  `app/simulator`, `tests`).
- Настройка FastAPI-приложения, конфигурация окружения (.env), Docker + docker-compose
  (app + postgres).
- Базовые модели SQLAlchemy и Alembic-миграция под сущности из раздела 9 ТЗ.

## Этап 2 — Ядро движка: барабаны и RNG
- Реализация RNG-модуля на `secrets`/`os.urandom` за интерфейсом (чтобы был легко заменяем
  позже под сертифицированный RNG).
- Генерация результата спина: 5 барабанов × 3 ряда, выбор символа на каждой позиции по весам
  из конфига.
- Юнит-тесты: при заданных весах распределение символов на больших выборках соответствует
  ожидаемому (статистический тест, не точное равенство).

## Этап 3 — Оценка выигрыша
- Line-pay: оценка совпадений по активным paylines слева направо, с поддержкой wild-замещения.
- Count-pay: оценка scatter/bonus символов по количеству на поле, независимо от линий.
- Явное правило без двойного начисления (тип символа в конфиге определяет механику).
- Юнит-тесты на оба типа отдельно и на смешанный кейс (line-pay + count-pay в одном спине).

## Этап 4 — Плагинная система бонус-фич
- Реализуй интерфейс `BonusFeature` (протокол/абстрактный класс) как описано в разделе 6.1
  ТЗ: `is_triggered`, `execute`, `get_config_schema`.
- Реализуй по этому интерфейсу: Free Spins, Hold and Win, Bonus Buy, Gamble, Jackpot (раздел
  6.2) — каждую в отдельном модуле, с юнит-тестами.
- Реестр фич (feature registry), через который движок узнаёт, какие фичи активны для
  конкретной игры/конфига, без хардкода списка в ядре.

## Этап 5 — API
- `POST /api/v1/spin`, `POST /api/v1/session/start`, `GET /api/v1/session/{id}/state`,
  `POST /api/v1/gamble` — по контракту из раздела 8.1.
- Админ-эндпоинты из раздела 8.2 (CRUD символов/весов/paytable/paylines, вкл/выкл фич,
  запуск симуляции, история спинов, версионирование конфига).
- Pydantic-схемы для всех запросов/ответов, автодокументация через `/docs`.
- Интеграционные тесты API (pytest + httpx/TestClient).

## Этап 6 — Симулятор RTP
- CLI-скрипт и/или админ-эндпоинт: прогон N спинов на NumPy, отчёт по разделу 7 ТЗ (RTP,
  hit frequency, вклад каждой механики отдельно, распределение выигрышей, отдельный RTP для
  bonus buy).
- Регрессионный тест: при неизменном конфиге RTP по новому прогону не отличается от
  сохранённого baseline больше чем на заданный процент.

## Этап 7 — Логирование и аудит
- Append-only запись `SpinRecord` на каждый спин с полным контекстом (версия конфига,
  ставка, результат, выигрыш, RNG-данные).
- Эндпоинт/отчёт для сверки фактического RTP за период с целевым.

## По ходу работы
- Пиши тесты вместе с кодом каждого этапа, а не в конце.
- Не переусложняй раньше времени (YAGNI) — но не отходи от принципа "вся математика в
  конфиге, не в коде" (раздел 2 ТЗ) — это ключевое требование.
- В конце каждого этапа — короткое резюме: что сделано, какие решения принял сам (и почему),
  что осталось открытым.
