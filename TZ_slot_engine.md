# ТЗ: Backend-движок слот-машины (Python)

## 1. Цель и контекст

Разработка серверного игрового движка слот-машины на Python. Это база, которая будет
развиваться дальше: новые темы, новые фичи, потенциально несколько игр на одном движке.
Клиентская часть (визуал, анимации) в текущий скоуп **не входит** — только бэкенд-логика,
отдаваемая через API.

Референс по жанру и уровню сложности механик: слот *"For the Love of Aphrodite"* (DreamPlay) —
классическая сетка 5×3, смесь line-pay и scatter/count-pay символов, фичи типа Free Spins.
Референс используется только как ориентир по сложности, не как техническая копия.

## 2. Ключевые принципы архитектуры

- Всё, что влияет на математику игры (RTP, частота выигрышей, суммы выплат) — вынесено в
  конфигурацию, а не зашито в код.
- Бонус-механики реализованы как отдельные модули с единым интерфейсом ("плагины"), которые
  можно включать/выключать и настраивать через админку — **без деплоя нового кода**.
- RTP управляется через веса выпадения символов, а не через хардкод вероятностей.
- Движок server-authoritative: клиент никогда не влияет на результат спина, весь расчёт — на
  сервере.

## 3. Технологический стек (предложение, обсуждаемо)

- Python 3.12+
- FastAPI — REST API (async, автогенерация OpenAPI/Swagger)
- Pydantic v2 — валидация конфигов и схем запросов/ответов
- PostgreSQL — хранение конфигураций, истории спинов, отчётов симуляций
- SQLAlchemy + Alembic — ORM и миграции
- Redis (опционально) — сессии игроков, кэш активного конфига
- NumPy — быстрые Monte-Carlo симуляции для расчёта RTP
- pytest + pytest-cov — тестирование
- Docker / docker-compose — окружение и деплой

## 4. Игровая механика

### 4.1 Игровое поле

- 5 барабанов (reels) × 3 ряда (rows) — стандартная сетка 5×3.
- Каждый барабан — независимый набор весов: RNG выбирает символ на каждой позиции по весам
  этого барабана (физическая "лента" не обязательна, если не потребуется имитация reel strip).

### 4.2 Типы выигрышных механик (поддерживаются одновременно)

1. **Line-pay** — выигрыш за совпадение символов подряд слева направо на активной payline.
   Число и раскладка линий — настраиваемые (например, 20 фиксированных линий).
2. **Scatter / count-pay** — отдельные символы (скаттеры, бонус-символы) платят за количество
   на поле независимо от расположения и линий (например, 3+ в любом месте сетки).

Движок должен обрабатывать оба типа в одном спине и корректно суммировать итог. Правило
без двойного начисления: тип символа в конфиге явно определяет, участвует ли он в line-pay
или в count-pay (символ не может выигрывать одновременно по обеим механикам на одной и той
же позиции).

### 4.3 Wild-символы

- Замещают обычные символы в line-pay (кроме scatter/bonus, если явно не указано иное).
- Подтип wild (обычный / expanding / sticky / multiplier) задаётся конфигом символа; логика
  раскрывается в соответствующем бонус-модуле, если требуется.

## 5. Конфигурация игры (редактируется через админку без деплоя кода)

Для каждой игры конфиг включает:

- **Символы** — id, имя, тип (regular / wild / scatter / bonus), вес на каждом барабане,
  paytable (выплата за 3/4/5 совпадений).
- **Барабаны** — веса символов по каждому из 5 барабанов.
- **Линии выплат** — список активных paylines (координаты по рядам для каждого барабана).
- **Ставки** — min/max bet, номинал на линию или total bet, шаг ставки.
- **Целевой RTP** — ориентир для симулятора (не гарантия "на лету").
- **Активные бонус-модули** — список включённых фич + параметры каждой (см. п.6).

Конфиг хранится в БД и **версионируется** — важно для аудита: "какой конфиг был активен в
момент конкретного спина".

## 6. Бонус-модули (плагинная архитектура)

### 6.1 Общий интерфейс

Каждый модуль реализует единый интерфейс, например:

```python
class BonusFeature(Protocol):
    feature_id: str

    def is_triggered(self, spin_result, config) -> bool: ...
    def execute(self, game_state, config) -> FeatureResult: ...
    def get_config_schema(self) -> dict: ...  # для валидации параметров в админке
```

Это даёт:
- вкл/выкл фичи в конфиге игры без деплоя;
- настройку параметров фичи (число скаттеров для триггера, число респинов, множители и т.д.)
  через админку;
- добавление новых типов фич в будущем как отдельных модулей, без изменения ядра.

**Важное допущение**: через админку настраиваются параметры уже реализованных в коде фич
(вкл/выкл + значения параметров), а не создание новой логики "с нуля" без участия
разработчика — это стандартный подход в индустрии (так устроены RGS). Визуальный конструктор
произвольной логики — отдельный, значительно больший скоуп.

### 6.2 Фичи первой очереди (набор по умолчанию)

- **Free Spins** — триггер по N+ scatter, начисление X бесплатных спинов, опционально
  retrigger, опционально множитель выигрыша во время фриспинов.
- **Hold and Win** — символы с денежным значением "залипают" на поле, N респинов, каждый
  новый символ обнуляет счётчик, суммирование по завершении.
- **Bonus Buy** — покупка входа в фичу за фиксированную цену (в X ставок), с **отдельным
  RTP-профилем** для этого режима (обязательно считается отдельно в симуляторе).
- **Gamble** — риск удвоить выигрыш (угадать цвет/карту), с лимитом попыток или максимальной
  суммой.
- **Jackpot** — фиксированный (несколько уровней) или прогрессивный (накопительный пул).

Каждая фича — отдельный модуль, независимый от остальных, тестируемый изолированно.

## 7. Математическая модель и симулятор RTP

Так как RTP управляется весами, а не хардкодом, обязателен инструмент проверки:

- **Симулятор**: прогоняет N млн спинов (число конфигурируемо) на заданном конфиге и считает:
  - фактический RTP (сумма выплат / сумма ставок);
  - hit frequency (% спинов с выигрышем);
  - вклад в RTP каждой механики отдельно (база / free spins / hold&win / jackpot) —
    критично для понимания, откуда берётся итоговый RTP;
  - распределение выигрышей (гистограмма, max win, оценка волатильности);
  - для bonus buy — отдельный RTP этого режима.
- Доступен как CLI-скрипт и как действие в админке ("прогнать симуляцию для текущего
  конфига" → отчёт).
- Пока фактический RTP по симуляции не попадает в допустимый диапазон от целевого — конфиг
  не должен уходить в прод (предупреждение, финальное решение — за админом).

## 8. API

### 8.1 Игровые эндпоинты

- `POST /api/v1/spin` — тело: `game_id`, `session_id`, `bet_amount`, опционально
  `feature_buy_id`. Ответ: сетка символов, выигрышные линии, суммы по линиям/механикам,
  итоговый выигрыш, состояние активной фичи (например "free spins: осталось 9"), новый баланс.
- `POST /api/v1/session/start` — создание игровой сессии (баланс, game_id).
- `GET /api/v1/session/{id}/state` — текущее состояние сессии.
- `POST /api/v1/gamble` — отдельный запрос для gamble-фичи после выигрыша.

### 8.2 Админ-эндпоинты

- CRUD по символам, весам, paytable, paylines.
- Вкл/выкл и настройка параметров бонус-модулей.
- Запуск симуляции RTP и получение отчёта.
- Просмотр истории спинов / логов (аудит).
- Версионирование конфига (кто/когда менял, откат к предыдущей версии).

Все ответы — JSON, схемы через Pydantic, автодокументация через FastAPI `/docs`.

## 9. Модель данных (основные сущности)

- `Game` — игра (с расчётом на несколько игр на одном движке в будущем).
- `GameConfig` (версионированный) — символы, веса, paytable, paylines, ставки, target RTP.
- `Symbol` — id, тип, веса по барабанам, paytable.
- `Payline`.
- `FeatureConfig` — тип фичи, enabled, параметры (JSON).
- `Session` — игрок/анонимная сессия, баланс, currency.
- `SpinRecord` — полный лог спина: версия конфига, ставка, результат, выигрыш, timestamp,
  RNG-seed/proof (для аудита).
- `SimulationRun` — параметры и результаты прогона симулятора.

## 10. RNG и честность результата

- RNG — криптографически стойкий (`secrets` / `os.urandom`), не `random.Random` со слабым
  сидом.
- Каждый спин логируется детерминированно (входные веса + результат) — для воспроизведения
  и объяснения исхода при аудите.
- На будущее (при выходе на реального оператора/казино) понадобится сертификация RNG
  независимой лабораторией (GLI-19 / iTech Labs и т.п.) — сейчас закладываем архитектуру так,
  чтобы RNG был легко заменяемым модулем (интерфейс, а не жёстко зашитая реализация).

## 11. Логирование и аудит

- Каждый спин — неизменяемая (append-only) запись с полным контекстом: версия конфига,
  ставка, результат, выигрыш, сработавшие фичи.
- Логи должны позволять пересчитать фактический RTP за период "по факту" и сверить с планом
  (симуляцией).

## 12. Нефункциональные требования

- Все игровые расчёты — исключительно на сервере.
- Целевая производительность — уточняется отдельно по мере роста нагрузки (не оптимизируем
  преждевременно).
- Конфиг кэшируется в памяти/Redis, инвалидация при изменении в админке.
- Тестовое покрытие: unit-тесты движка выигрышных комбинаций (line-pay и count-pay — отдельно
  и вместе), unit-тесты на каждый бонус-модуль, интеграционные тесты API, регрессионный тест
  "симуляция не должна давать RTP, отличающийся от прошлого прогона больше чем на X% при
  неизменном конфиге" — защита от случайных багов в математике.

## 13. Что НЕ входит в скоуп (явные допущения)

- Визуальный клиент/фронтенд — не разрабатывается, только API-контракт для него.
- Платёжный шлюз / реальные деньги / KYC — не входит, баланс на этом этапе — внутренняя
  абстракция.
- Сертификация RNG у третьей стороны — задел на будущее, не в текущем скоупе.
- Визуальный конструктор бонус-фич для нетехнических людей — не входит; админка настраивает
  параметры уже написанных фич.

## 14. Открытые вопросы (решить до/в процессе разработки)

- Точное число и раскладка paylines.
- Финальный список символов и их paytable (тема игры, арт — отдельная задача).
- Точные параметры каждой бонус-фичи по умолчанию (сколько скаттеров, сколько респинов и
  т.д.) — можно взять типичные индустриальные значения как стартовые и подкручивать весами
  и параметрами дальше.
- Нужна ли поддержка нескольких валют/локалей на этом этапе.
